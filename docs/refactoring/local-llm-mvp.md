# 로컬 LLM 챗봇 MVP 설계·구현 기록

## 1. 범위

이번 단계는 벡터 DB와 범용 사내 검색을 제외하고, 로그인 사용자가 실제로 확인할 수 있는 최근 공지와 처리 대기 결재만 SQL로 조회해 로컬 LLM에 전달한다.

```text
React ChatPanel
        ↓ POST /api/ai/chat (SSE)
AiController
        ↓
AiService
   ├─ NoticeMapper: 전사 또는 사용자 부서 공지 5개
   ├─ ApprovalMapper: 현재 결재자의 대기 항목 5개
   └─ LocalLlmClient: Ollama /api/generate
```

## 2. 구현 내용

1. 질문은 공백 제외 1~500자로 제한한다.
2. 결재는 로그인 사번이 결재선에 있고 현재 상태가 `대기`인 문서만 조회한다.
3. 공지는 전사 코드 `999` 또는 로그인 사용자의 부서 코드와 일치하는 항목만 조회한다. 관리자는 전체 공지를 조회할 수 있다.
4. 조회 데이터와 사용자 질문을 분리하고, 조회 데이터 안의 지시를 실행하지 말라는 문장을 시스템 프롬프트에 포함했다.
5. JDK `HttpClient`로 Ollama 네이티브 API를 호출하며 별도 AI SDK는 추가하지 않았다.
6. Ollama JSON Lines를 읽는 즉시 SSE `token` 이벤트로 전달한다.
7. 완료 시 모델명, 첫 토큰 시간, 전체 응답 시간, 생성 토큰 수를 `done` 이벤트와 서버 로그에 남긴다. 질문 원문은 로그에 기록하지 않는다.
8. 연결 실패, 비정상 HTTP 응답, 시간 초과에는 내부 오류 대신 사용자용 안내를 보낸다.
9. 통합 테스트에서는 실제 모델을 호출하지 않고 `LocalLlmClient`를 가짜 응답으로 교체해 스트리밍과 권한 필터를 검증한다.

## 3. 설정과 실행

기본값은 Ollama의 `qwen3:4b` 모델이다. 환경 변수로 서버, 모델, 추론 모드, 시간 제한을 바꿀 수 있다.

```properties
ERP_AI_BASE_URL=http://localhost:11434
ERP_AI_MODEL=qwen3:4b
ERP_AI_THINK=false
ERP_AI_TIMEOUT_SECONDS=60
```

```bash
ollama pull qwen3:4b
ollama serve
./mvnw spring-boot:run
```

비추론 비교 모델은 다음처럼 실행한다.

```bash
ollama pull qwen3.5:2b
ERP_AI_MODEL=qwen3.5:2b ERP_AI_THINK=false ./mvnw spring-boot:run
```

Ollama가 중지되어 있어도 ERP의 다른 기능은 실행되며, 챗봇만 모델 상태 확인 안내를 표시한다.

## 4. 트러블슈팅

### 스트리밍 API인데 답변이 한 번에 표시될 수 있음

- 원인: 응답 라인을 `toList()`로 먼저 모으면 Ollama 응답이 끝날 때까지 토큰 소비가 시작되지 않는다.
- 해결: 응답 스트림의 `Iterator`를 순차 소비해 각 JSON 라인을 읽는 즉시 SSE로 전달했다.
- 확인 지표: 실제 모델 검증에서 첫 토큰 시간과 전체 응답 시간이 분리되어 기록되어야 한다.

### 다른 사용자의 결재·부서 공지가 프롬프트에 포함될 위험

- 원인: 전체 수신함이나 전체 공지 조회 메서드를 그대로 재사용하면 화면 권한과 AI 문맥 권한이 달라질 수 있다.
- 해결: 현재 결재자의 미처리 결재와 전사·본인 부서 공지만 반환하는 전용 Mapper 쿼리를 추가했다.
- 재발 방지: 가짜 LLM이 받은 프롬프트에 허용 데이터는 포함되고 다른 사용자·부서 데이터는 없는지 통합 테스트에서 확인한다.

### 테스트가 로컬 모델 상태에 따라 실패할 수 있음

- 원인: 실제 모델의 설치 여부, 모델 다운로드 상태, 생성 결과는 CI에서 일정하지 않다.
- 해결: 통합 테스트에서는 네트워크 경계인 `LocalLlmClient`만 가짜 응답으로 교체했다. DB 조회, 권한 필터, Controller SSE는 실제 코드로 실행한다.

### Qwen3 응답의 첫 토큰이 늦게 표시됨

- 재현 환경: Apple M5, 메모리 32GB, Ollama 0.33.0, `qwen3:4b` Q4_K 모델.
- 원인: 설치된 `qwen3:4b`는 Thinking 2507 모델이라 내부 추론이 끝난 뒤 최종 답변의 `response` 필드를 전송한다. 실제 첫 요청은 내부 생성 1,730토큰 때문에 첫 화면 토큰까지 48.5초가 걸렸다.
- 확인: Ollama 요청에 `think: false`를 넣어도 이 모델에서는 추론이 비활성화되지 않았고, 짧은 직접 요청도 1,007토큰과 27.4초가 소요됐다.
- 추가 현상: Ollama 재기동 직후 같은 공지 질문이 내부 추론 2,000토큰을 넘기며 60초 제한에 두 번 도달했다. 화면에는 오류 안내가 표시됐지만 답변 성공률과 첫 토큰 시간 모두 대화형 UX 기준에 부족하다.
- 현재 판단: 연결과 스트리밍 기능은 정상이나 기본 모델로 쓰기에는 지연 변동이 크다. 동일 질문 비교에서 `qwen3.5:2b` 비추론 모드가 더 빠르고 안정적이었다.

### 하이브리드 모델도 추론 모드에서는 느림

- 원인: `qwen3.5:2b`도 기본 추론 모드에서는 간단한 공지·결재 질문에 1,897~2,293개의 내부 생성 토큰을 사용했다.
- 현상: 3건 중 2건만 완료됐고 첫 토큰은 40.7~47.1초, 나머지 1건은 60초 제한을 넘었다. 완료된 결재 답변도 허용된 결재가 없다고 잘못 판단했다.
- 해결: Ollama 요청의 `think` 값을 `ERP_AI_THINK`로 제어하고 기본값을 `false`로 두었다. 비추론 모드에서는 3건 모두 1.6초 안에 완료됐다.

### 첫 메시지 전송 시 챗봇 화면이 사라짐

- 원인: 메시지 변경 때 실행되는 React `useEffect`가 `scrollIntoView()`의 반환값을 그대로 반환해 React 19가 다음 갱신 시 이를 정리 함수로 호출했다.
- 해결: 효과 본문을 중괄호로 감싸 반환값이 없도록 수정했다.
- 확인: 프로덕션 빌드 후 실제 브라우저에서 메시지를 전송해 패널이 유지되고 `답변 생성 중`과 시간 초과 안내가 정상 렌더링되는 것을 확인했다.

## 5. 성능 기록 기준

2026-09-23에 Apple M5, 메모리 32GB, Ollama 0.33.0, `qwen3:4b` Q4_K 환경에서 로그인 사용자 `2005002`로 최초 기준값을 측정했다.

| 질문 | SSE 토큰 이벤트 | 첫 토큰 | 전체 응답 | 생성 토큰 | 권한 외 데이터 |
| --- | ---: | ---: | ---: | ---: | --- |
| 최근 공지 요약해줘 | 12 | 48,496ms | 48,887ms | 1,730 | 없음 |
| 내가 처리할 결재 알려줘 | 35 | 13,066ms | 14,011ms | 516 | 없음 |
| 오늘 우선 처리할 업무가 뭐야? | 20 | 21,566ms | 22,081ms | 890 | 없음 |

- 세 요청의 첫 토큰 중앙값은 21,566ms, 전체 응답 중앙값은 22,081ms다.
- 전체 3,136토큰을 84.979초에 생성해 서버 기준 처리량은 약 36.9토큰/초다.
- 표본이 3건뿐이므로 p95로 표현하지 않는다.
- 다른 사용자 결재와 다른 부서 공지를 임시 표식 데이터로 추가한 뒤 세 응답 모두 미노출을 확인했고, 검증 후 해당 데이터는 삭제했다.
- Ollama 종료 상태에서는 HTTP 연결 자체는 유지한 채 SSE `error` 이벤트로 `로컬 AI가 응답하지 않습니다. 모델 실행 상태를 확인해 주세요.`를 7ms 안에 반환했다.

다음 측정도 아래 값을 같은 질문 세트와 같은 하드웨어 조건으로 저장한다.

1. 첫 토큰 시간(TTFT) p50·p95
2. 전체 응답 시간 p50·p95
3. 초당 생성 토큰 수
4. 시간 초과·실패율
5. 프롬프트 길이와 모델명

성능 개선 수치는 아래 동일 조건 3건 비교 범위에서만 사용하며 장기 운영 성능으로 일반화하지 않는다.

## 6. qwen3.5:2b 비교 결과

같은 사용자, DB, 질문, 하드웨어에서 `qwen3.5:2b`의 비추론 모드를 측정했다.

| 질문 | SSE 토큰 이벤트 | 첫 토큰 | 전체 응답 | 생성 토큰 | 권한 외 데이터 |
| --- | ---: | ---: | ---: | ---: | --- |
| 최근 공지 요약해줘 | 61 | 138ms | 1,503ms | 67 | 없음 |
| 내가 처리할 결재 알려줘 | 55 | 117ms | 1,264ms | 57 | 없음 |
| 오늘 우선 처리할 업무가 뭐야? | 63 | 119ms | 1,468ms | 66 | 없음 |

- 3건 모두 성공했으며 첫 토큰 중앙값은 119ms, 전체 응답 중앙값은 1,468ms다.
- `qwen3:4b` 기준값보다 첫 토큰은 99.45% 감소해 181.2배 빨랐고, 전체 응답은 93.35% 감소해 15.0배 빨랐다.
- 전체 190토큰을 4.235초에 생성해 애플리케이션 지표 기준 약 44.9토큰/초다.
- 허용된 결재는 정확히 안내했고 다른 사용자 결재와 다른 부서 공지는 노출하지 않았다.
- 공지 질문에 본인 결재까지 함께 언급하는 과잉 응답이 있어, 기본 모델 변경 전 질문 의도에 맞는 자료만 사용하도록 프롬프트를 한 차례 더 다듬는다.
- 표본이 각 조건 3건뿐이므로 장기 성능이나 p95 개선으로 일반화하지 않는다.
