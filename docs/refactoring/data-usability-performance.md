# 의존성·데이터·사용성 보완과 실제 성능 측정

2026-10-22 구현·검증 완료. 기존 P1 세션 회수·본인 결재 차단·이력 보존을 유지하며 데이터·사용성을 보완했다. 사용자의 최종 선택에 따라 성능 검증은 **포트폴리오용 1천 건·3반복**으로 마무리했다. 추가 대량 측정은 중단하고 전용 앱·DB를 모두 종료했다. 기존 개발 DB·첨부와 실행 앱은 유지했다.

## 변경 계약

| 범위 | 기대 결과 |
|---|---|

| 결재 첨부 | 교체·삭제가 커밋된 뒤 참조 없는 이전 파일만 제거. 롤백·거절은 기존 파일 보존 |
| 공지 파일명 | 요청의 내부 저장 파일명을 신뢰하지 않고 서버가 저장한 이름만 사용. 실패 cleanup으로 다른 파일을 삭제하지 않음 |
| 비밀번호 | null·빈 문자열·공백 수정은 기존 암호 유지. 실제 변경 후 새 암호 로그인과 화면 초기화 확인 |

## 의존성 결과

Vite를 8.3.5, source-map-js를 1.2.2로 갱신했다. 기존 React·React DOM·Vite React plugin의 버전은 유지했다. `npm ci` 재설치 후 `npm audit --json`의 High·전체 보고 건수는 모두 2에서 0으로 바뀌었다. [원본 감사와 해시](review-evidence/dependencies-20261022.json)에 기록했다. 이는 실행 시점에 알려진 권고의 검사이며 기능 정상 여부는 별도 회귀로 확인한다.

수정 버전 근거는 [Vite에 포함된 launch-editor 권고](https://github.com/vitejs/launch-editor/security/advisories/GHSA-698v-4r3x-3vcv)와 [source-map-js 권고](https://github.com/advisories/GHSA-68fv-2mgg-jv7q)다.

## 구현·독립 검증

Backend Architect(`/root/data_backend`)는 Service·Controller·Mapper와 실제 MySQL·WebSocket 회귀를, Frontend Developer(`/root/usability_frontend`)는 화면과 브라우저 회귀를 담당한다. Performance Benchmarker(`/root/performance_tools`)는 전용 생성기·API·SQL·메신저·브라우저 측정을 담당한다. 주 에이전트는 의존성·통합·순차 빌드·환경 제어·실행 결과 대조를 맡는다. 다른 담당자의 기존 변경을 유지하고 같은 빌드·DB 제어를 병렬 실행하지 않는다.

## 1천 건 실제 측정

[포트폴리오용 결과](../../performance/results/20261022T103945Z-2fe863/README.md)에 조건·원문·분모를 모았다. native 전용 루트에서 공지·결재·메시지를 각각 1천 건 생성하고 같은 fixture로 3회 반복했다. 읽기 API는 작업자 1명·5명, 메시지는 1개·5개 방, 브라우저는 cold/warm을 분리했다. 기본 CI에서 생략한 성능 테스트를 이 단계에서 명시 실행했다.

| 측정 | 정상 / 시도 | 실패 |
|---|---:|---:|
| API 11개 사례 | 9,900 / 9,900 | 0 |
| 수신자 메시지 전달 | 1,800 / 1,800 | 0 |
| 재접속 복구 | 18 / 18 | 0 |
| 메시지 DB·중복 검사 / 초기 상태 검사 | 18 / 18, 6 / 6 | 0 |
| 브라우저 6개 사례 × cold/warm | 360 / 360 | 0 |
| SQL 계획 | 24개 SELECT × ANALYZE 3회 | 원문 보관 |

5작업자 대시보드 API의 반복별 p95는 8.229·7.828·7.754ms, 5개 방의 메시지 전달은 2.623·1.696·1.538ms였다. 검색의 실제 클릭→결과 DOM 완료 표본 60개의 p95는 44.3ms다. 브라우저 longtask는 관측 0개였다. LCP 123개는 미관측 null이며 0으로 바꾸지 않았다. 이 로컬 합성 표본을 일반 정확도·상용 처리량·운영 SLA·현장 INP로 표현하지 않는다.

첫 성능 환경은 긴 소켓 경로 때문에 MySQL 시작 전에 중단됐다. 전용 루트 이름을 짧게 고쳐 새 환경으로 측정했다. 이후 큰 규모 실행은 사용자 요청으로 중단·평가 제외했으며, [범위·종료 기록](../../performance/results/20261022T103945Z-2fe863/portfolio-scope.json)에 남겼다. 도구 기본값도 1천 건으로 낮췄다.

## 병목 판단과 남은 개선

1천 건에서 오류나 longtask로 재현된 성능 장애는 없다. 상대적으로 큰 API 비용은 대시보드·완료 결재 조회였고, 대시보드는 상태별 COUNT 4회와 수신 COUNT 1회를 수행한다. SQL 원문을 근거로 남겼지만 지금 COUNT 통합이나 새 인프라가 필요하다고 판정하지 않았다. 메신저 화면 준비 시간은 클릭·패널 표시·이력 렌더를 포함하므로 transport 전달 시간과 구분한다.

포트폴리오에는 문제 재현→공통 원인 수정→실제 MySQL·WebSocket·브라우저 회귀와 1천 건 실측까지 설명하면 된다. 남은 작은 개선 후보는 사원 상세의 키보드 진입·모바일 메뉴 포커스다. 첨부 cleanup은 커밋 후 프로세스 내 처리이므로 I/O 실패·직후 프로세스 중단 때 고아 파일이 남을 수 있으며 경고 로그를 남긴다. 과거 고아 파일의 일괄 삭제는 하지 않았다. 실제 AI 재비교·원격 CI·다른 장비·운영 배포는 이번에 실행하지 않았다.
