# ERP 리팩터링 종합 기록

- 작업 기간: 2026-09-17 ~ 2026-09-18
- 기준 브랜치: `main`
- 목적: 레거시 ERP를 안전하게 리팩터링하고, 포트폴리오에서 설명할 수 있는 테스트·성능·트러블슈팅 근거를 남긴다.
- 수치 원칙: 동일 조건에서 실제 측정한 값과 SQL 호출 수처럼 코드로 확인 가능한 값만 사용한다. 측정하지 않은 동시 처리량과 사용자 체감 성능은 개선됐다고 주장하지 않는다.

## 2. 단계별 개선 내용

### 2.1 Spring Boot 실행 환경과 로그인 리팩터링

적용 사항:

1. Spring Boot 애플리케이션 진입점과 `application.properties`를 추가했다.
2. Maven Wrapper와 VS Code 실행·디버그 구성을 추가했다.
3. 로컬 MySQL을 Docker Compose로 실행하도록 구성했다.
4. Spring Security의 폼 로그인을 적용했다.
5. 신규 비밀번호는 BCrypt로 저장하고, 기존 MD5 비밀번호는 정상 로그인 시 BCrypt로 자동 전환되도록 했다.
6. 비밀번호 변경 시 현재 비밀번호 확인과 신규 BCrypt 저장을 Service 트랜잭션 안에서 처리했다.
7. 로그인 공개 접근, 보호 페이지 리다이렉트, 로그인 실패, 기존 비밀번호 자동 전환을 통합 테스트로 고정했다.

보안 개선:

- 평문 또는 단일 레거시 해시 방식에 머물지 않고 BCrypt를 기본 인코더로 사용한다.
- 전체 사용자 비밀번호를 일괄 초기화하지 않고, 정상 로그인한 계정부터 점진적으로 재해시한다.
- 인증 성공·실패와 로그아웃 동작을 Spring Security 흐름으로 통일했다.

측정 기록:

초기 기준과 로그인 리팩터링 후 측정은 모두 기본 시드 데이터와 단일 사용자 순차 50회 요청을 사용했다. 다만 초기 기록에는 워밍업 횟수가 명시되지 않았고 공지·결재 평균에 큰 최대값의 영향이 있어, 아래 값은 참고 기록으로만 사용한다.

| 화면 | 초기 평균 / p95 | 로그인 리팩터링 후 평균 / p95 |
|---|---:|---:|
| 메인 | 2.86ms / 3.67ms | 2.75ms / 3.08ms |
| 공지 | 4.30ms / 3.36ms | 3.39ms / 3.76ms |
| 결재 | 4.10ms / 3.32ms | 3.08ms / 3.56ms |

프로세스 RSS는 223,952KB에서 293,488KB로 약 31.1% 증가했다. 기동 상태와 측정 조건이 충분히 통제되지 않았으므로 메모리 회귀로 단정하지 않고, 향후 동일 JVM 옵션과 안정화 시간을 적용해 다시 측정해야 한다.

### 2.2 테스트 DB 격리와 CI

적용 사항:

1. 통합 테스트가 개발용 MySQL 대신 Testcontainers가 생성한 MySQL을 사용하도록 변경했다.
2. 테스트마다 필요한 데이터를 준비하고 종료 시 컨테이너와 함께 제거되도록 했다.
3. GitHub Actions에서 Node 22로 React를 빌드한 뒤 Java 21로 `./mvnw --batch-mode test`를 실행하도록 구성했다.
4. `main` 브랜치 push와 pull request에서 동일한 검증이 수행되도록 했다.

효과:

- 테스트 중 관리자 비밀번호나 업무 데이터가 개발 DB에서 바뀌는 위험을 제거했다.
- 로컬 환경에 남아 있는 데이터와 테스트 순서에 따른 결과 차이를 줄였다.
- 프론트엔드 빌드 실패와 백엔드 회귀를 원격 저장소 단계에서 함께 확인할 수 있게 했다.

### 2.3 전자결재 구조 리팩터링

구조:

```text
ApprovalController
        ↓
ApprovalService
        ↓
ApprovalMapper
        ↓
approval_mapper.xml
```

적용 사항:

1. Controller에 섞여 있던 결재 작성, 결재선 검증, 요청, 승인, 반려, 상태 전이 규칙을 `ApprovalService`로 이동했다.
2. 직접 SQL 세션 호출을 `ApprovalMapper`로 통일했다.
3. 상태 변경과 여러 테이블 갱신을 `@Transactional` 경계 안에서 실행했다.
4. 역할이 불분명했던 `approvalDTO`를 제거하고 요청·응답과 도메인 역할을 분리했다.
5. 작성, 결재선, 승인, 반려, 최종 상태, 사용자별 접근, 실패 시 롤백을 통합 테스트로 고정했다.

코드 구조로 확인한 SQL 개선:

| 처리 | 이전 | 현재 | 감소율 |
|---|---:|---:|---:|
| 승인·반려 상태 변경 | UPDATE 5회 | UPDATE 2회 | 60% |
| 결재 상세 조회 | SELECT 4회 | SELECT 3회 | 25% |
| 사용자별 상태 집계 | 행별 상관 서브쿼리 최대 6회 | GROUP BY 집계 1회 | 반복 조회 제거 |

로컬 응답 시간 측정:

| 지표 | Before | After 1차 | After 재측정 | Before 대비 재측정 |
|---|---:|---:|---:|---:|
| 결재 목록 평균 | 2.80ms | 3.41ms | 2.90ms | +3.6% |
| 결재 목록 p95 | 3.75ms | 4.04ms | 3.71ms | -1.1% |
| 결재 목록 최대 | 4.40ms | 5.43ms | 4.36ms | -0.9% |

기본 시드 데이터에서는 응답 시간 개선이 유의미하지 않았다. 이 단계의 핵심 성과는 작은 데이터에서의 밀리초 단축이 아니라 SQL 왕복 감소, 트랜잭션 원자성, 테스트 가능한 구조 확보다.

### 2.4 권한 강화, 공지사항·사원관리 리팩터링

적용 사항:

1. 공지사항과 사원관리도 Controller → Service → Mapper 구조로 변경했다.
2. `noticeDTO`, `userDTO`를 제거하고 Service와 Mapper의 책임을 명확히 했다.
3. 관리자 전용 사원관리 API를 URL 보안과 Service 권한 검사로 보호했다.
4. 결재 작성자·현재 결재자 권한을 서버에서 검사해 다른 사용자의 수정과 상태 변경을 차단했다.
5. 첨부파일 다운로드 전에 해당 결재 문서 열람 권한을 확인했다.
6. 공지 삭제를 GET 요청에서 POST + CSRF 검증 방식으로 변경했다.
7. 사원 조회 응답과 HTML에서 비밀번호 해시를 제거했다.
8. 공지 등록·수정·삭제와 사원 등록·수정·삭제를 트랜잭션으로 묶었다.

코드 구조로 확인한 SQL 개선:

| 처리 | 이전 | 현재 | 감소율 |
|---|---:|---:|---:|
| 공지 대상 부서 3개 저장 | INSERT 3회 | 다중 VALUES INSERT 1회 | 66.7% |
| 공지 10개 일괄 삭제 | DELETE 10회 | `IN` DELETE 1회 | 90% |
| 다음 사원번호 탐색 | SELECT 최대 100회 | 집계 SELECT 1회 | 최대 99% |
| 공지 작성자 표시 | 행별 작성자 서브쿼리 | JOIN 1회 | N+1 형태 제거 |

로컬 응답 시간 측정:

| 화면 | 지표 | Before | After 재측정 | 변화 |
|---|---|---:|---:|---:|
| 공지 목록 | 평균 | 3.90ms | 2.21ms | -43.3% |
| 공지 목록 | p95 | 5.31ms | 2.83ms | -46.7% |
| 사원 목록 | 평균 | 2.86ms | 2.75ms | -3.8% |
| 사원 목록 | p95 | 3.54ms | 3.80ms | +7.3% |

공지 목록 수치는 같은 측정 구간에서 변경하지 않은 결재 목록도 함께 빨라져 JVM·DB 상태의 영향을 배제할 수 없다. 따라서 포트폴리오에는 관측 결과로만 사용하고, 코드 변경만의 인과 효과로 표현하지 않는다. 사원 목록은 유의미한 응답 시간 개선이 확인되지 않았다.

### 2.5 React/Vite와 반응형 프론트엔드 전환

적용 사항:

1. Bootstrap 4·5 의존을 제거하고 CSS Grid/Flex 기반 반응형 레이아웃으로 교체했다.
2. React 19와 Vite 8을 도입하되 기존 Spring Security 세션과 `.do` 주소를 유지했다.
3. 로그인, 공통 레이아웃, 메인, 결재, 공지, 사원관리, 내 정보, 비밀번호 변경을 React 화면으로 전환했다.
4. Spring MVC 모델 데이터에 직접 의존하지 않도록 JSON API를 Dashboard·Approval·Notice·User 컨트롤러로 분리했다.
5. 기존 파스텔 색상과 업무 화면의 정보 구조는 유지하면서 둥근 사이드바, 투명 카드, 다크 모드, 챗봇 버튼을 적용했다.
6. 서비스 소개용 반응형 랜딩 페이지를 추가했다.
7. 프론트 전환 전후 화면을 캡처하고 서버 응답 시간을 같은 스크립트로 측정했다.

서버 HTML 응답 시간:

| 화면 | 지표 | Before | After | 변화 |
|---|---|---:|---:|---:|
| 메인 | 평균 | 2.78ms | 1.09ms | -60.8% |
| 메인 | p95 | 3.78ms | 1.48ms | -60.8% |
| 결재 목록 | 평균 | 3.00ms | 0.88ms | -70.7% |
| 결재 목록 | p95 | 3.92ms | 1.08ms | -72.4% |

이 수치는 JSP 서버 렌더링과 일부 DB 조회 대신 React 셸 HTML을 반환하게 된 서버 응답 시간이다. JavaScript 다운로드, 렌더링, API 요청까지 포함한 브라우저 전체 체감 속도는 아니므로 Lighthouse 또는 Web Vitals 측정 전에는 사용자 체감 성능이 같은 비율로 개선됐다고 표현하지 않는다.

React 최초 전환 시 번들은 JavaScript 249.59KB(gzip 76.96KB), CSS 39.76KB(gzip 8.87KB)였다. 메신저와 전체 사원관리 화면이 포함된 현재 빌드는 JavaScript 308.18KB(gzip 90.87KB), CSS 49.52KB(gzip 10.46KB)다. 최초 전환 대비 JavaScript gzip은 13.91KB, CSS gzip은 1.59KB 증가했으며 이후 기능 추가 시 계속 추적한다.

### 2.6 사내 메신저 MVP

구조:

```text
React 메신저 UI
        ↓ STOMP/WebSocket 또는 REST
ChatController / ChatMessageController
        ↓
ChatService
        ↓
ChatMapper
        ↓
MySQL
```

적용 사항:

1. 사용자 두 명 사이에 하나의 1:1 대화방을 생성하도록 `(user_a, user_b)` 유일 제약을 적용했다.
2. STOMP/WebSocket과 내장 SimpleBroker로 실시간 텍스트 메시지를 전달한다.
3. 메시지를 MySQL에 먼저 저장한 뒤 구독자에게 전달해, 새로고침이나 재접속 후 REST 이력 조회로 복구할 수 있게 했다.
4. 읽음 시각과 안 읽은 메시지 수를 저장·조회한다.
5. 연결이 끊어지면 3초 후 재접속하고 대화 이력을 다시 불러온다.
6. 클라이언트가 보낸 발신자 값을 신뢰하지 않고 인증된 `Principal`을 발신자로 사용한다.
7. 방 목록, 이력 조회, 메시지 전송, 읽음 처리마다 참여자 권한을 검사한다.
8. `(room_no, message_no)`와 `(room_no, sender_usernum, read_at)` 인덱스를 추가했다.

검증 결과:

- React 프로덕션 빌드 성공
- 전체 통합 테스트 18개 통과
- 대화방 비참여자 REST 접근 403 확인
- 브라우저 두 세션에서 실시간 수신, 새로고침 후 이력 유지, 읽음 배지 변경 확인

아직 측정하지 않은 항목:

- 동시 WebSocket 연결 수
- 초당 메시지 처리량
- 메시지 전달 p95 지연 시간
- 메시지 저장 DB p95
- 재접속 중 오류율과 메시지 유실률

위 값이 없으므로 SimpleBroker의 한계나 Redis Pub/Sub 도입 효과는 아직 주장하지 않는다. 단일 서버 부하 측정에서 한계가 확인될 때만 Redis를 추가한다.

## 3. 통합 테스트 확장 기록

| 단계 | 테스트 수 | 추가로 고정한 핵심 흐름 |
|---|---:|---|

| 전자결재 | 10 | 작성, 결재선, 승인·반려, 최종 상태, 권한, 롤백 |

최종 테스트는 인증, 권한, 트랜잭션, 데이터 영속성처럼 장애 시 영향이 큰 흐름을 중심으로 구성했다. UI 세부 스타일은 통합 테스트 대상에 포함하지 않고 빌드와 브라우저 확인으로 검증했다.

## 4. 트러블슈팅 기록

### 4.1 통합 테스트가 개발 DB의 관리자 비밀번호를 변경함

- 증상: 로그인·비밀번호 테스트 후 개발 계정으로 로그인할 수 없었다.
- 원인: 통합 테스트가 개발용 MySQL에 직접 연결됐다.
- 해결: Testcontainers 전용 MySQL과 테스트 시드로 완전히 분리했다.
- 재발 방지: CI와 로컬 테스트 모두 같은 격리 구성을 사용한다.

### 4.2 Controller에 업무 규칙과 SQL 호출이 분산됨

- 증상: 결재 상태 변경 규칙을 한 곳에서 추적하기 어렵고, 승인·반려 SQL이 중복됐다.
- 원인: Controller가 요청 처리, 권한 검사, 상태 전이, Mapper 호출을 함께 담당했다.
- 해결: 상태 전이와 권한을 Service로 이동하고 Mapper를 통해서만 SQL을 호출했다.
- 결과: 승인·반려 UPDATE를 5회에서 2회로 줄이고 트랜잭션 경계를 명확히 했다.

### 4.3 결재 상태 변경 중 일부 SQL만 반영될 수 있음

- 증상: 여러 테이블을 갱신하는 중간 단계가 실패하면 부분 반영될 가능성이 있었다.
- 원인: 업무 단위가 아니라 개별 SQL 단위로 실행됐다.
- 해결: 결재 요청·승인·반려를 `@Transactional` Service 메서드로 묶고, 잘못된 결재자 처리 시 전체 롤백 테스트를 추가했다.

### 4.4 한글 소스 인코딩이 CP949/EUC-KR로 혼재함

- 증상: Java 파일 수정과 컴파일 과정에서 한글이 깨질 수 있었다.
- 원인: 일부 VO 파일과 IDE 설정의 문자 인코딩이 UTF-8로 통일되지 않았다.
- 해결: 관련 VO 7개와 Eclipse 프로젝트 설정을 UTF-8로 변환했다.
- 재발 방지: 저장소의 소스 인코딩을 UTF-8 기준으로 유지한다.

### 4.5 `target`의 오래된 클래스 때문에 깨끗한 빌드와 결과가 다름

- 증상: 이전 빌드 산출물이 남아 소스와 실제 실행 클래스가 달라질 수 있었다.
- 원인: 추적되던 생성 파일과 오래된 컴파일 결과가 남아 있었다.
- 해결: 생성 산출물 23개를 Git 추적에서 제외하고 `clean test`로 검증했다.

### 4.6 첫 성능 측정과 재측정 값이 다름

- 증상: 전자결재 리팩터링 직후 평균 응답 시간이 오히려 증가했다.
- 원인: 로컬 JVM 워밍업, DB 캐시, 백그라운드 프로세스 영향을 받는 밀리초 단위 측정이었다.
- 해결: 첫 결과를 삭제하지 않고 재측정 결과와 함께 보존했다.
- 판단: 단일 실행의 좋은 수치만 선택하지 않고 SQL 호출 수와 반복 측정을 함께 근거로 사용한다.

### 4.7 로그인만 하면 관리자 기능에 접근할 수 있음

- 증상: 일반 사용자가 사원관리 요청을 직접 호출할 여지가 있었다.
- 원인: 로그인 여부 중심의 URL 검사만 있었고 객체 단위 권한 검사가 부족했다.
- 해결: Spring Security 역할 제한과 Service 관리자 검사를 함께 적용했다.

### 4.8 다른 사용자의 결재 문서·첨부파일 접근 가능성

- 증상: URL이나 문서 번호를 바꾸면 타인의 문서 수정·첨부파일 요청을 시도할 수 있었다.
- 원인: 화면 버튼 노출 여부에 권한을 의존했다.
- 해결: 작성자, 현재 결재자, 최종 공개 상태를 Service에서 검사하고 첨부파일 다운로드에도 같은 정책을 적용했다.
- 검증: 일반 사용자 수정 차단과 첨부파일 접근 통합 테스트를 추가했다.

### 4.9 암호화된 비밀번호가 사원관리 응답과 화면에 노출됨

- 증상: 비밀번호 해시가 조회 결과와 HTML 입력값에 포함됐다.
- 원인: DB 엔티티를 화면 모델로 그대로 사용했다.
- 해결: 조회 SQL과 응답에서 `userpw`를 제외하고 화면 필드를 제거했다.

### 4.10 공지 삭제가 GET 요청과 화면 버튼에 의존함

- 증상: 상태 변경 요청이 URL 호출만으로 실행될 수 있었다.
- 원인: 삭제를 GET으로 처리하고 관리자 여부를 UI에 의존했다.
- 해결: POST + CSRF로 변경하고 URL과 Service에서 관리자 권한을 검사했다.

### 4.11 다음 사원번호를 최대 100번 조회함

- 증상: 사용 가능한 번호를 찾기 위해 반복 SELECT가 실행됐다.
- 원인: 애플리케이션 반복문으로 중복 여부를 하나씩 확인했다.
- 해결: 집계 SELECT 1회로 후보 번호를 계산하고 DB 기본 키가 최종 중복을 방지하도록 했다.
- 한계: 동시 등록 충돌이 실제로 관측되면 sequence 테이블 또는 재시도 정책을 검토한다.

### 4.12 React 전환 후 CSRF 통합 테스트 4개 실패

- 증상: 서버 렌더링 화면에 있던 CSRF 토큰을 찾지 못해 테스트가 실패했다.
- 원인: React 셸로 바뀌면서 기존 hidden input이 사라졌다.
- 해결: Spring Security 토큰을 meta와 hidden input으로 노출해 기존 폼과 React 요청이 함께 사용하도록 했다.

### 4.13 결재 상세에서 목록으로 이동할 때 JavaScript 오류 발생

- 증상: 화면 이동 시 `TypeError`가 발생했다.
- 원인: `useEffect` 콜백이 Promise를 반환해 React가 이를 정리 함수로 처리하려 했다.
- 해결: effect 내부에서 비동기 함수를 호출하되 Promise 자체를 반환하지 않도록 수정했다.

### 4.14 랜딩 페이지 오른쪽 미리보기 카드가 비뚤어짐

- 증상: 업무 대시보드 미리보기 카드가 다른 요소와 수평으로 맞지 않았다.
- 원인: 데스크톱 스타일에 `transform: rotate(1deg)`가 적용됐다.
- 해결: 회전 효과를 제거하고 반응형 구간의 불필요한 `transform` 재정의도 함께 정리했다.

### 4.15 메신저 대화방 매핑 결과가 `null`임

- 증상: DB에는 대화방이 있지만 `ChatRoomVO`의 일부 값이 매핑되지 않았다.
- 원인: MyBatis의 snake_case 컬럼과 Java 프로퍼티 매핑을 암묵적 설정에 의존했다.
- 해결: 대화방과 메시지 조회에 명시적 `resultMap`을 적용했다.

### 4.16 메신저 플로팅 버튼이 세로로 깨짐

- 증상: 새 채팅 버튼의 글자가 세로로 줄바꿈됐다.
- 원인: 기존 공통 채팅 버튼 CSS 선택자가 새 메신저 버튼에도 적용됐다.
- 해결: 기존 규칙의 적용 범위를 좁혀 두 컴포넌트의 스타일이 충돌하지 않게 했다.

### 4.17 로컬 통합 테스트에서 Docker 연결 실패

- 증상: Testcontainers가 MySQL 컨테이너를 시작하지 못했다.
- 원인: Docker Desktop이 실행되지 않았다.
- 해결: 로컬 테스트 전 Docker Desktop 실행을 필수 조건으로 문서화했다.

### 4.18 일부 업무 화면에 새 UI가 적용되지 않음

- 증상: 메인·결재 목록·상세는 새 React UI였지만 결재 작성·수신·전체승인·공지사항은 구형 사이드바와 회색 JSP 화면으로 표시됐다.
- 원인: 대상 URL이 React 메인 셸을 벗어나 각 JSP의 사이드바·푸터·다크모드·챗봇을 다시 렌더링했다. 공통 CSS만 공유해도 서로 다른 DOM과 JavaScript 컴포넌트 때문에 화면과 동작을 완전히 같게 만들 수 없었다.
- 해결: 결재 작성·수정·수신·전체승인과 공지 목록·상세·작성 GET 요청을 모두 `app.jsp`로 연결했다. 기존 Service·Mapper를 재사용하는 JSON API를 추가하고 React `AppLayout` 안에서 각 화면을 렌더링해 사이드바, 다크모드, 사내 메신저, AI 챗봇을 하나의 컴포넌트로 통합했다. JSP fallback 사이드바에는 메뉴 전체 너비 규칙도 추가했다.
- 검증: 최신 서버를 별도 포트로 실행해 결재수신·결재작성·전체승인·공지 목록·상세를 순서대로 이동했다. 모든 화면에서 같은 사이드바와 다크모드·메신저·AI 버튼이 유지됐고, 메신저 WebSocket 연결과 공지 상세 직접 새로고침도 정상 동작했다. `npm run build`와 Testcontainers MySQL 기반 통합 테스트 18개도 통과했다.

### 4.19 사원관리·비밀번호 변경 화면만 JSP로 남음

- 증상: 사원 목록·상세·등록·수정, 내 정보, 비밀번호 변경에서 공통 사이드바와 플로팅 기능이 다른 구조로 렌더링됐다.
- 원인: 기존 JSP와 jQuery가 화면별 DOM, 이벤트, Spring MVC 모델을 직접 소유해 React 공통 레이아웃을 재사용할 수 없었다.
- 해결: 해당 `.do` GET 요청은 모두 동일한 `app.jsp` 셸로 연결하고, 조회·등록·수정·삭제·비밀번호 변경을 `/api/users` JSON API로 분리했다. 화면은 `frontend/src/user` 모듈에서 렌더링하고 공통 `AppLayout`을 사용한다.
- 보안: `/api/users/me`와 비밀번호 변경은 로그인 사용자에게, 나머지 사원관리 API는 관리자에게만 허용한다. 비밀번호 해시는 JSON 응답에 포함하지 않는다.
- 검증: 일반 사용자의 관리자 API 403, 본인 API 접근, 관리자 CRUD, BCrypt 비밀번호 변경을 통합 테스트에 포함했다.

### 4.20 단일 프론트·API 파일의 책임이 커짐

- 증상: `App.jsx`와 `FrontendApiController`에 화면 및 도메인 API가 계속 누적됐다.
- 원인: React 전환 초기에는 빠른 검증을 위해 하나의 파일에 라우팅과 화면을 모았다.
- 해결: 프론트는 `layout`, `approval`, `notice`, `user`, `messenger`, `ai`로 나누고 `App.jsx`는 라우팅 조합만 담당하게 했다. 백엔드는 `DashboardApiController`, `ApprovalApiController`, `NoticeApiController`, `UserApiController`로 분리하고 기존 Service·Mapper를 그대로 재사용했다.

## 5. 포트폴리오에 사용할 수 있는 검증된 성과

다음 표현은 현재 저장소의 테스트, SQL 구조, 측정 파일로 근거를 제시할 수 있다.

1. 레거시 Spring MVC ERP를 Spring Boot 4.1.1 실행 구조로 전환하고 Spring Security·BCrypt를 적용했으며, 기존 MD5 계정은 정상 로그인 시 자동 재해시하도록 구현했다.
2. 개발 DB를 직접 변경하던 통합 테스트를 Testcontainers MySQL로 격리하고 핵심 회귀 테스트를 4개에서 18개로 확장했다.
3. 전자결재 승인·반려 처리의 UPDATE를 5회에서 2회로 60% 줄이고, 트랜잭션 실패 시 전체 롤백을 검증했다.
4. 공지 대상 저장 SQL을 3회에서 1회로 66.7%, 공지 10건 삭제 SQL을 10회에서 1회로 90%, 사원번호 탐색 SELECT를 최대 100회에서 1회로 최대 99% 줄였다.
5. Bootstrap을 제거하고 React/Vite 반응형 UI로 점진 전환해 메인 서버 HTML 평균 응답 시간을 2.78ms에서 1.09ms로 60.8%, 결재 목록은 3.00ms에서 0.88ms로 70.7% 줄였다. 이 수치는 브라우저 전체 로딩 시간이 아닌 서버 HTML 응답 기준이다.
6. Spring WebSocket, SimpleBroker, MySQL로 1:1 메신저 MVP를 구현하고 DB 선저장, 재접속 이력 복구, 읽음 처리, 안 읽음 수, 대화방 참여자 권한을 통합 테스트와 브라우저에서 검증했다.

사용하면 안 되는 표현:

- 동시 사용자 처리량이 개선됐다는 주장
- 메신저가 메시지를 초당 특정 건수 처리한다는 주장
- Redis보다 SimpleBroker가 더 빠르다는 주장
- 서버 HTML 응답 감소율을 사용자 체감 로딩 속도 감소율로 바꾼 표현
- 로컬 소량 데이터 결과만으로 운영 환경의 성능을 보장한다는 표현

## 6. 다음 측정 과제

우선순위대로 다음 근거를 추가한다.

1. 메신저 부하 테스트: 동시 연결 수, 메시지/초, 전달 p95, 저장 p95, 오류율, 유실률
2. 브라우저 성능: Lighthouse와 Web Vitals의 LCP, INP, CLS, 초기 JavaScript 크기
3. 대용량 DB 성능: 결재·공지·메시지 데이터를 늘린 뒤 EXPLAIN, 평균, p95, p99 측정
4. 동시성 검증: 같은 사용자 쌍의 방 동시 생성, 사원번호 동시 발급, 같은 결재 건의 중복 승인
5. 메모리 기준 재측정: 동일 JVM 옵션, 안정화 시간, GC 조건으로 RSS와 heap 비교
